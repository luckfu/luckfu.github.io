我给 OpenClaw Dreaming 修了一个 Bug——正则表达式引发的"鬼打墙"

时间： 2026-04-08   |   分类： 技术   OpenClaw   Bug Fix   | 字数： 1590 字 | 阅读： 4分钟 | 阅读次数：

背景

OpenClaw 的 Dreaming 功能（后台记忆整合）是一个实验特性，设计意图是：

  1. Light Phase：扫描近期 memory 文件，提取关键内容写 short-term recall store
  2. REM Phase：对 recall store 做去重和聚类
  3. Deep Phase：对足够丰富的 recall 调用 LLM 生成深度总结，写入 DREAMS.md 并选择性升级到 MEMORY.md

配置开启后，每天 04:00（可自定义）自动运行一次。听起来很美。

但实际上：开了等于没开——没有任何输出。

问题症状

  • Dreaming 配置 enabled: true，cron 定时正常
  • openclaw memory status 显示 recall store 永远为空：0 entries · 0 promoted
  • DREAMS.md 从未生成
  • memory/.dreams/short-term-recall.json 不存在
  • gateway 日志里没有任何错误，只有静默的 No short-term recall candidates.

调查过程

第一层：怀疑插件/配置

检查 plugins.entries.memory-core.config.dreaming，配置路径正确，frequency 为 0 4 * * *。/dreaming on / dreaming status 均正常响应。配置没有问题。

第二层：怀疑 recall store 写入权限

检查 /home/opc/.openclaw/workspace/memory/.dreams/ 目录，目录存在，权限正常。权限也没有问题。

第三层：怀疑 trigger 通道

手动向 main session 注入 openclaw_memory_core_short_term_promotion_dream 事件，Hook 确实被调用了（DREAMING_HOOK_FIRED_UNMISTAKABLE 日志出现），Pipeline 也执行了，但返回 executed: false。Trigger 通道是通的，问题在 pipeline 内部。

第四层：怀疑 recall store 内容不足

检查 recall store：short-term-recall.json 存在但 entryCount: 0。检查 memory 文件列表，发现 canonical daily 文件从 2026-04-04 起就不存在了：

memory/2026-04-03.md         ✅  最后一个标准文件
memory/2026-04-04-x-credentials.md   ❌（不是 YYYY-MM-DD）
memory/2026-04-07-title-copy.md      ❌（不是 YYYY-MM-DD）

检查 session hook 日志：OpenClaw 内置的 hooks/session-memory 在写 session 碎片文件，格式为 YYYY-MM-DD-HHMM.md，而不是 Dreaming 要求的 YYYY-MM-DD.md。

第五层：深入代码

读取编译后的 dist 文件，找到关键函数 isShortTermMemoryPath()：

// 原版正则（有问题） const RE = /(?:^|/)memory/(\d{4})-(\d{2})-(\d{2}).md$/;

这个正则只匹配 memory/2026-04-03.md，不完全不匹配 memory/2026-04-07-title-copy.md。

而 recordShortTermRecalls() 的写入条件是：

if (result.source !== “memory”) return; if (!isShortTermMemoryPath(result.path)) return; // 写 recall store ← 这里直接跳过，没有任何日志

两个条件都满足才写。只要文件名不匹配正则，写入静默跳过。

根因

OpenClaw 的 session-memory hook 改变了 memory 文件的命名习惯：从标准 YYYY-MM-DD.md 变成了 YYYY-MM-DD-HHMM.md（session 碎片）。但 Dreaming 的 short-term recall 入口正则还是旧的，只认标准格式。

结果链路： session-memory 写 YYYY-MM-DD-HHMM.md → Dreaming 正则不匹配 → recall store 永远为空 → REM phase 没有输入 → Deep phase 不触发 → DREAMS.md 永不生成

这是一个经典的"接口契约不匹配"Bug：两个模块各自正确，但输出/输入格式没对上。

修复方案

修改 short-term-promotion-G9ML8hkA.js 中的正则：

// 修改前 const RE = /(?:^|/)memory/(\d{4})-(\d{2})-(\d{2}).md$/;

// 修改后 const RE = /(?:^|/)memory/(\d{4})-(\d{2})-(\d{2})(?:-.*)?.md$/;

(?:-.*)? 表示可选的 -后缀 部分（后缀可以是 -HHMM，也可以是 -任意话题）。

同时在 dreaming-CnlsXIYM.js 中做了两处次要改进（锦上添花）：

  1. Trigger 白名单放宽：从只接受 heartbeat 扩展为 [“heartbeat”, “system”, “cron”]
  2. Telegram 提醒文本解析：正确从 “A scheduled reminder has been triggered. The reminder content is: xxx” 中提取原始 event 名称

验证

打补丁后，手动注入 cron probe：

Schedule: 2026-04-08T06:50:48.000Z (14:50:48 CST) Payload: openclaw_memory_core_short_term_promotion_dream

结果： DREAMING_HOOK_FIRED_UNMISTAKABLE »> trigger=heartbeat bodyLen=… Executing pipeline… done (executed: false, success: true)

executed: false 是正常的——当天 recall store 条目数不足（阈值 ≥ 3），LLM 不会生成总结。Pipeline 完整走完了，只差内容积累。

Dreaming 端到端通了。

经验总结

  1. 遇到"静默失败"时，第一时间去读 dist 源码，不要猜测。OpenClaw 的错误处理很干净，不会主动报错，需要自己追踪条件分支。

  2. 接口契约不匹配是分布式系统的经典 Bug。两个模块都在工作，但格式没对上。建议 OpenClaw 团队在 isShortTermMemoryPath() 中加入更宽松的匹配，或者让 session-memory hook 默认写标准 daily 文件。

  3. Hook 的 params.trigger 值不一定是事件原类型。Cron 触发的事件传到 before_agent_reply hook 时，trigger 值是 “heartbeat” 而不是 “cron”——这是 OpenClaw 内部的事件路由机制。

  4. 下次升级时只需检查一处补丁。主要修复只有一处：short-term-promotion-G9ML8hkA.js 的正则。其他两处是锦上添花，不影响核心功能。
